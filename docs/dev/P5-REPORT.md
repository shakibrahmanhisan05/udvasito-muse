## The three P4 carry-over fixes

1. **PushRegistrar (F1, S2-for-pilot).** `app/_layout.tsx` passed `{token, platform, deviceLabel}` to `push:registerExpoToken`, whose validator accepts only `{token}`; Convex rejected every call and the client's swallowed catch hid it — Android Expo tokens were never recorded. **Choice: trim the client to `{token}`** — specs §6.4 defines the function's contract as `{token}` (the server derives everything else), so the client was wrong, not the validator. The now-unused `deviceLabel` import was removed. Regression test (`tests/p5-client-contract.test.ts`) reads both source files and asserts the call's argument keys exactly equal the validator's keys, so any future drift fails CI instead of silently no-oping again; it also asserts the web-push registration passes its full documented shape.
2. **Redaction separators (F2, S3 — landed before any `GEMINI_API_KEY` exists).** The phone pattern now allows the separator class `[\s()./-]*` between digits (dots `01812.345.678`, parentheses, slash, double spaces, fully-spaced digits, and a separator between the `1` and the `[3-9]` digit), in Latin and Bangla digits; `extractContactPhone` reuses the same shape so the regex-only contact path cannot diverge; the grouped-ID rule also absorbs dash/dotted groups (the cheap case of review F5). Every variant is asserted against the **exact outbound payload** (`buildIntakePayload`), and dates, landlines and ward numbers are asserted NOT to be eaten.
3. **AI-response voiding (F3, S3).** `parseGeminiResponse` previously voided only contiguous Latin-digit phones; it now uses the shared `containsPhoneNumber()` (digit-normalising), so a spaced or Bangla-digit phone in a verbatim-merged field (e.g. `area`) voids the whole AI response. Tests cover every separator variant in `area` plus a clean-response control.

## Bugs caught during the build (fixed in-slice)

- **sign-in.tsx practice gate could never open (pre-existing, P1).** The stub read `appConfig?.features.practiceAreaEnabled`, but `public.appConfig` returns `practiceAreaEnabled` at the **top level** — so the practice entry never rendered, and the sheet behind it was a note with a Done button. Fixed: correct field + a working ID+PIN form.
- **Audit pagination vs Convex limits.** Convex allows only one `.paginate()` per query and query builders are single-use; the first design (loop-paginate with post-filtering) is impossible. The viewer now uses an offset cursor over a bounded newest-first scan (the `admin.people.search` pattern), with the practice-wall filter applied before slicing so pages are never short or leaky.
- **aiCalls has no `by_created` index and different field names than assumed** (`inputRedacted`, `errorKind`, required `output`/`latencyMs`/`isDemo`). The AI status/usage queries collect + range-filter instead (exact at quota-capped volumes).
- **usageCounters index is (service, day), not (day, service)** — the monitor gathers today's counters per known service through the index.
- **convex-test's monotonic clock** bit twice (fixtures must be built chronologically; a "previous LA day" AI call inserted late landed in today). Fixtures reordered; time-sensitive assertions use ranges where the backend clock, not the fake clock, is authoritative.

## Interpretation notes

1. **Stats definitions (chosen where specs leave the exact cut).** Public `requestsHelped` = requests closed with `closeReason: "fulfilled"`; `donationsConfirmed` = requests with ≥1 donor-confirmed donation (G2 wording); `donorsByGroup` counts live donors. Admin: `availableNow` = live ∧ availability "available" ∧ eligibleFrom ≤ now; first-accept speed counts "now"-urgency requests only; the pilot-district filter applies only when `pilotDistrictIds` is non-empty (OQ-12 unseeded); availability freshness is over active-profile donors within S-28 (90 days); campaign sign-ups come from `profiles.campaignCode` (V07).
2. **Coverage is conservative.** Duty intervals are rebuilt from `volunteer_duty_changed` events (P5 added `vpId` to the event props; pre-P5 events lack it and are ignored) plus currently-on-duty rows. A currently-off volunteer closes any open interval at their last event — coverage is never invented. Known under-report edge: `admin.people.setStatus/setRole` patch `onDuty=false` without a duty event.
3. **Dismiss also notifies.** The brief says every decision notifies the affected person; for dismiss the NTF-14 action text is "Report reviewed — no action taken" — the subject learns the report about them was reviewed and closed. The alternative (silent dismiss) would make the DoD's audit+notification matrix unprovable for dismiss; the notification is factual and closes the loop for the reported person.
4. **AI log spans the wall deliberately.** Practice and real calls share one Gemini quota, so `ai.status` counts both and `ai.log` shows both, each row badged `isDemo`. An admin investigating quota burn must see practice calls; the log contains no phone numbers by construction (redaction precedes the call).
5. **Practice funnel is computed live**, not from `statsSnapshots` — the snapshot key union is only `"public" | "admin"` (P0 schema), and adding a third key was unnecessary schema churn for ≤10 accounts.
6. **Audit demo-scoping is actor-based** because `auditLog` has no `isDemo` field: rows whose actor profile is on the other side of the wall are hidden; system rows (no actor) show for both.
7. **`demo_account_removed` is a small extension of the §6.9 audit-action list** (which enumerates `demo_account_created`, `demo_pin_reset`, `demo_reset` but no removal). An unaudited account deletion would be worse than the extension; flagged here for the team's spec pass.
8. **Practice provisioning is action-based by necessity** — mutations cannot call the Better Auth API. The data half is a superadmin-checked internal mutation so the invariants (≤10 accounts, hospital, audit) hold even if the action layer changes; the action adds the credential half and rolls the data back on any failure.
9. **Onboarding completes the practice account honestly.** `completeOnboarding` is create-or-patch by `authUserId`, so a linked practice profile is patched in place (keeps `isDemo`/`practiceId`, takes the person's **real** phone) — practice accounts are real accounts on real phones, per D-R4; there are no fake phone numbers anywhere in the flow.

## Gaps & flags (honest list)

1. **PRD §2.3 judging acceptance test on staging is NOT done** — it needs P5 deployed to staging (parent/human step, like every phase's go-live list). Everything testable locally is tested; the staging run (real Google sign-in, practice sign-in on a phone, a live request end-to-end) remains for the parent flow.
2. **Live practice sign-in (ID+PIN) is unverifiable in the harness** — the Better Auth component has no convex-test registration, so `signUpEmail`, the hooks and session revocation are exercised only by their surrounding unit tests (prepare/link/gate/isolation). First staging verification must cover: create account → sign in with ID+PIN → 5 wrong PINs lock → disable area refuses sign-in. Also required in the Convex env: `BETTER_AUTH_EMAIL_ENABLED=1` (without it, account creation honestly fails `ERR_METHOD_DISABLED`).
3. **Unkeyed admin copy (I18N-GAPS §4) is rendered as specs prose via module consts** — the moderation/audit screen titles, the SCR-A03 decision labels, the SCR-A09 action labels (Create / New PIN / Remove / Reset practice data) and the "fixed"/"hidden" markers exist in specs only as prose, with no i18n keys and no Bangla. Following the SCR-A05 precedent (role/status values rendered raw), they are held in clearly-commented consts pending member 3's key review; the eslint `i18next/no-literal-string` gate stays green without weakening it. Still omitted rather than invented: the SCR-A02 empty state ("Nothing to review. 🎉"), the SCR-A01 "Stats are being prepared" banner (the screen offers recompute instead), and most admin row micro-labels (screens lean on keyed headings + raw values).
4. **Client screens are lean** (as in P1–P4): the audit viewer's actor/date filters are server-supported but the client exposes the action filter (offset cursors are forward-only; "back" restarts the list — documented in the screen); the usage manual-entry form takes raw service/metric names; the dashboard's campaign/coverage cards have no keyed headings (gap 3).
5. **Session revocation on practice-area disable is best-effort** — the scheduled internal action deletes Better Auth sessions per practice user and swallows per-user failures; the sign-in gate refuses new sessions regardless, so a revocation failure never re-opens the area.
6. **S-37 `noShowPenalty.count` semantics (P2-REVIEW S3-F3)** still needs the product decision from Shakib/team — untouched by P5, as in P4.
