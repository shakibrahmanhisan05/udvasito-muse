## What was built

- **Redaction (X05)** — `convex/rules/redaction.ts` completed: phones in EN/BN digits, `+880` and `01…` forms (incl. spaced groups), emails, ID numbers (10/13/17 digits, incl. spaced groups), names after cue words — Bangla labels are matched as **whole tokens** (`নাম` inside `নামাজ` must not trigger), longest-first (`রোগীর নাম`, `রোগী`, `রোগীর`, `নাম`, `জনাব`, `বেগম`), Latin labels (`patient`, `patient's`, `name`, `mr.`, `mrs.`) plus Banglish `rogir nam`; an expanded diagnosis list (stroke, diabetes, tuberculosis, pregnancy + BN forms, word-boundaried). **Dengue is deliberately NOT redacted** — it is an operational form field (`isDengue`), not in PRD §6.2's diagnosis list. Also exports `extractContactPhone` — the regex-only path by which a contact number may be taken from a message; the AI is never asked for it and never trusted with it.
- **F-206 Intake (R03)** — `convex/rules/intakeParser.ts`: digit-normalised, token-based (Bangla-safe tokeniser, see bugs) extraction of blood group (symbolic → Bangla-letter → spelled EN/Banglish, with `not_sure`/`any` phrases checked first), component (platelet words → platelets; blood/রক্ত/rokto and donor words → whole blood), units (digit near ব্যাগ/bag, phones stripped first, "doctor hasn't decided" → null), hospital (token-overlap scoring over refData names+aliases **only** — the parser can never invent a hospital; generic tokens like "medical" are down-weighted and can never win alone), area (explicit place-name mention, else the matched hospital's metro-thana area), neededBy kinds, dengue. `intake.parse` action flow: VAL-13 length gate → guard mutation (auth, G6 `assertActive`, 10/hour rate limit, settings, quota state, refData — one mutation) → regex phone extraction on the **original** text → rules parse → **only if a required field (blood group, units, hospital) is still missing** and `ai.features.intake` is on and a model is seeded and `GEMINI_API_KEY` is set and the daily quota (LA day, `ai.limits.liteDaily`) and the S-29 per-draft cap (`aiIntakeCallsPerRequest` = 2, counted per `clientId`) allow it: reserve quota atomically → **redact** → POST the exact payload built by `convex/ai/gemini.ts` `buildIntakePayload` (specs §6.10 prompt + JSON schema, temperature 0) → strictly validate the response (**a phone-shaped string anywhere in the AI output voids the whole response**) → merge into **null fields only** (AI hospital names are matched back through the same refData matcher; unmatched names are dropped). Every call is logged in `aiCalls` with the **redacted** input only, plus an `ai_call` event whose props are `{feature, ok}` — no text. AI problems never throw: the action returns the rules result with `aiError: "disabled" | "quota" | "unavailable"`.

## Bugs the new tests caught (fixed in-slice)

- **Bangla tokeniser shattered words** — the intake tokeniser's character class omitted `\p{M}`; Bangla vowel signs are combining marks, so words split mid-syllable and hospital matching silently failed on Bangla text. Fixed by including marks.
- **ASCII `\b` after Bangla letters** — JS `\b` is ASCII-only; the units regex never matched "২ ব্যাগ" at the boundary. Replaced with a `(?![\p{L}\p{N}])` lookahead.
- **Generic alias "Medical" matched everything** — a hospital alias consisting of a generic token ("Medical") substring-matched any text mentioning a medical college. Fixed: generic tokens are down-weighted (0.4), a candidate with no distinctive token matched can never win, and the substring shortcut requires a distinctive token.
- **Area false positives from the nationwide places list** — short Bangla area names prefix-matched unrelated words (করিম→Karimganj, পরশু→Parashuram). Fixed by scoping refData areas to upazilas of hospital-served districts (the server does the same) and making Bangla area matching one-directional.
- **Random IDs eaten by the phone rule** — in the 500-message generator, a random 13-digit ID can contain a phone-shaped substring and is redacted as a phone first. Still fully removed from the payload (the invariant that matters); the generator now leads IDs with "9" and the accounting assertion is `ids + phones ≥ 2` per message.
- **convex-test harness nuance (not a product bug)** — `finishInProgressScheduledFunctions` does not drain actions scheduled *by other scheduled functions* in this harness version; the web-push end-to-end test uses `finishAllScheduledFunctions`, which does. Production scheduling is unaffected.

## Interpretation notes

1. **Schema change (widening only):** `aiCalls.clientId` changed from required to `v.optional(v.string())`. The S-29 cap (`aiIntakeCallsPerRequest` = 2 calls per request draft) needs a per-draft counter; the draft's `clientId` is the only stable key available before the request exists, and `aiCalls` is the table the quota guard already reads. Backwards-compatible; all pre-existing rows are unaffected (none exist yet — P4 is the first writer).
2. **The 14 area misses are a data gap, not a parser bug.** The fixtures name the **neighbourhood** (Agrabad, Andarkilla, Mehedibag); the parser names the correct **thana** from places data (Double Mooring, Kotwali) — and two cases (bn-08, en-10) expect *no* area where the parser offers the matched hospital's thana. Neighbourhood names exist in no reference data the parser is allowed to use (inventing them would break the "parser never invents" rule). The fix is member 3 adding neighbourhood rows to the places data; the parser will pick them up unchanged. Documented in `docs/intake-eval.md`.
3. **AI fixtures are hand-authored stand-ins, not model output.** `tests/fixtures/intake-ai.json` was written from the message texts alone under the system prompt's "null when not clearly stated — never guess" rule (including well-known hospital localities a competent model would know). They measure the *pipeline* (redaction → payload → validation → merge → scoring), not Gemini's real accuracy; the live number can only be measured once a key exists (human step). The eval doc says this in its method section.
4. **`ai.models.lite` is seeded `""` = unconfigured.** The action treats an empty model as AI-unavailable (honest) rather than guessing a model name; spike S4's model pick must be seeded as a setting when the key is provisioned. Both the key (`GEMINI_API_KEY`) and the model seed are human/ops steps — the code path is fully tested with fixtures/mocks in their absence.
5. **S-29 is counted per request draft (`clientId`)**, not per created request — the cap exists to stop one draft from burning the shared daily quota through repeated "Fill the form" taps, and the draft is the only identity a parse call has. The client passes the same `clientId` it will post with.
6. **Web Push transport is additive.** `notifyUser` keeps exactly one `notifications` row per event; Expo and Web Push are transports of that record. The notification's stored status/failure still describes the Expo attempt (as in P1–P3); web delivery outcomes live on the subscription rows (`failures`, `lastSuccessAt`) per §7.6.
7. **Offline detection is "no app error code".** Convex app errors always carry an `ERR_*` code; transport failures don't. A post that fails validation server-side therefore shows its error (correct), while a post that never arrived queues (correct). The queued payload is the member's own form input on their own device.
8. **Client rules parse needs `intake.refData`** because `hospitals.list` does not return aliases; the new member query returns exactly the parser's refData shape (same builder the action uses), so on-device and server parses cannot drift.

## Gaps & flags (honest list)

The sender, encryption, registration and bookkeeping are unit/integration-proven with throwaway keys; the last mile (browser push services) is not exercisable from this environment.
2. **Live Gemini is unverifiable here** — no `GEMINI_API_KEY` exists (Shakib must create one in Google AI Studio and set it in the Convex dashboard; it must never travel through chat). Until then the action honestly reports `unavailable`, and the eval's AI pass is fixture-based (note 3).
3. **Alert-guide brand steps (DEP-08)** — Samsung/Xiaomi/etc. battery-whitelisting steps are member 3's unkeyed copy; the screen ships the keyed generic steps only. Same pattern as P1/P2 unkeyed-copy gaps.
4. **Neighbourhood places data** — the area-field fix (note 2) needs member 3 to add neighbourhood rows (Agrabad, Andarkilla, Mehedibag, …) to the places dataset; no code change needed afterwards.
5. **Pre-existing bug noticed, out of scope:** `app/_layout.tsx`'s `PushRegistrar` calls `push:registerExpoToken` with `{token, platform, deviceLabel}` but the mutation validates only `{token}` — the extra args fail validation and are swallowed by `.catch(() => {})`, so Expo token registration silently no-ops from the client. The server function and its tests are correct; the client call needs trimming to `{token}` (one-line fix, left untouched here to keep P4's diff inside its scope — flagged for P5 or a drive-by).
6. **Voice on web** depends on the browser's Speech API (Chrome-only in practice) and on native speech services (Android may route audio to Google services — that is the platform's recogniser, disclosed by the OS permission flow; the F-205 story accepts `expo-speech-recognition`). No audio ever reaches UDVASITO servers: only the transcript the member sees and edits.
7. **P3-review follow-ups F2/F6 were NOT in this brief and were not touched:** hotline coverage-definition mismatch (F2) and push-token 60-day inactivity pruning (F6, also P3-REPORT gap 6) remain open for a later phase.
8. **Client screens are lean** (as in P1–P3): the outbox has no queue-management UI (queued posts are visible as a count on My Requests and flush automatically); the intake box offers no per-field undo — the pre-filled form itself is the editing surface, per F-1103.
